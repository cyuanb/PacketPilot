# 补件复检

## 适用范围
用于已有检查后的补件核验、版本变更比较和再次预检。不能仅因用户说“已经补齐”就关闭问题。

## 操作流程
1. 调用 get_case_context，取得当前修订、启用要求、资料版本和 previous_findings；明确旧结论只供对照，不是当前事实。
2. 核对哪些输入已变化。当前目录无法证明具体旧文件内容时，不推断修改细节；没有可比较的旧结果时明确说明本次只是当前状态检查。
3. 调用 run_checks 对当前快照重新检查。使用完整重查作为保守基线，不跳过新增材料可能解决或引入的问题。
4. 对变化涉及的语义要求调用 read_document 阅读当前材料，按 next_offset 继续读取；record_semantic_findings 必须逐项提供 semantic_coverage 与支持证据。不可读、归属不明或未覆盖部分保持 unknown。
5. 按 requirement_id 对照新旧结果，区分已解决、仍未解决、新增问题、尚不可比较。要求已变更或适用条件改变时说明比较边界，不能把要求删除当作材料合格。
6. 指出哪些人工确认已随版本变化失效，需要再次查看原件。例外说明、他人复核意见和已提交记录都不能替代当前核验。
7. 输出变化摘要与行动，不手动关闭问题。问题状态由服务端根据当前完整结果同步；运行过时或部分失败时不得宣称补件闭环已完成。

## 输出格式
### 本次检查范围
写明当前版本、旧结果是否可比以及读取限制。
### 补件后的变化
使用“已解决 / 仍待处理 / 新增 / 无法比较”分组，引用实际前后结论。
### 依据
列出当前材料名、页码及支持片段；无旧材料证据时只比较结论，不捏造原文差异。
### 下一步
按优先级列出剩余补件、背景确认和人工复核，说明何时需要再次预检。

## 边界
用户聊天中的新事实需 propose_facts 后确认；未知条件调用 ask_user。不自动切换资料版本、启用新要求、代签、对外提交或声称接收方已收到。
