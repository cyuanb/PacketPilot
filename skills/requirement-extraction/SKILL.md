# 通知要求提取

## 适用范围
用于提取通知、整理材料清单或建立要求草稿。输出是草稿，不能自行启用，不对尚未启用的要求发布正式预检结论。

## 操作流程
1. 调用 get_case_context，确认通知来源、读取状态、当前要求版本和用户要处理的通知范围。没有可读通知时调用 ask_user 请求导入或校订，不生成空想清单。
2. 对涉及的每份通知调用 read_document。用 next_offset 分页读取；尚未阅读的部分不得宣称已覆盖，读取预算不足时先说明覆盖范围并请求拆分通知。
3. 提取必需与建议材料、适用条件、数量、格式、日期、字段一致性、签名或人工要求。每项记录文档标识、页码和逐字引文，不能从文件名、场景建议或外部常识推断规则。
4. 使用现有 Requirement Schema 表达规则：存在性、格式/大小/页数、字段/日期、语义或人工核对；需要组合时采用 group 和明确 children，避免重复归属、循环或无来源子项。
5. 条件不明保留待确认，日期不明不要猜起算日；签名、盖章、真实性必须保留人工核对。不同通知参数冲突应并列保留来源并指出冲突，不代替用户决定政策优先级。
6. 调用 save_requirement_draft 保存草稿。只有工具返回成功及 draft_id 才说已保存；失败时按具体错误修正，不重复发送相同无效参数。
7. 汇总来源、草稿内容与待确认事项，引导用户到申请要求页审阅、试运行并显式启用。不得将草稿视作当前生效要求。

## 输出格式
### 阅读范围
列出已读通知与未覆盖部分（如有）。
### 要求草稿
列出草稿版本、主要要求与引用位置；指出自动核对和人工核对的区别。
### 待确认事项
列出条件、来源冲突或日期歧义，没有则写“未发现需补充确认的条目”。
### 下一步
明确说明“请审阅并启用草稿，之后再开始预检”。

## 约束
引文必须能被服务端在相应通知页定位。不得编造通知、自动启用、伪造完整阅读或把模型建议包装成通知原文。
